### 바뀐 결정과 이유
- 일정을 월(앱)·화(테스트)·수(검토)로 재편, 목·금은 예비.
- 앱 언어 Python(FastAPI), API와 Processor를 한 서비스로 합침. 만들 것을 줄여 산출물에 시간을 쓰기 위해.
- R-09 신설: 던지기 요청에 라운드 번호를 넣어 중복 요청을 거부. 대표 TC "중복 던지기 1회 처리"의 근거 규칙.
- 매치별 seed를 DB에 저장. 인스턴스 수와 상관없이 같은 결과가 나오게 하기 위해.
- 통계 화면은 Chart 옆에 같은 값을 표로도 보여줌. Chart(canvas)는 자동화로 값을 읽기 어렵기 때문.
- 로드밸런서(nginx) 추가: `--scale app=N`으로 인스턴스 수를 바꿔 측정하기 위해 (TC-004).

- 이슈 유형에 Spec Issue(SPEC-xxx)를 추가. 중도 이탈 매치(3승 전에 페이지를 닫음)가 "진행 중"으로 영구히 남는데 명세에 규칙이 없음 → 기대 결과를 쓸 수 없으므로 **SPEC-001**로 리포트하기로 함. 앱은 고치지 않음.
  - 유형 이름은 처음 "Spec Update"로 정했다가 **"Spec Issue"**로 바꿈. 명세 변경은 여러 부서의 합의가 필요하므로 QA가 올리는 시점에는 "업데이트"가 아니라 "이슈"이기 때문. QA 권고안과 PO 결정도 분리해 적기로 함.
  - 화요일 흐름: 유저 시나리오에 "중도 이탈" 추가 → 해당 TC를 Blocked(명세 없음)로 표시 → DB 조회로 증거 확보 → `05-defects/SPEC-001.md` 작성 → 명세 4장에 미결 항목으로 링크

- 게임 화면 주사위를 숫자 대신 **점(pip)**으로 표시 (작성자 요청). 합계가 아래 숫자로 따로 보이므로 가독성 문제 없음. 자동화는 글자 대신 각 주사위의 `data-value` 속성으로 눈 값을 읽는다.
- 화면 HTML에 `Cache-Control: no-store` 추가. 앱을 다시 빌드한 뒤에도 브라우저가 예전 화면을 보여주는 문제가 있었기 때문 (테스트가 옛 화면을 검증하는 것을 막기 위해).

- 게임 화면 맨 위에 **게임 규칙 안내**를 추가 (작성자 요청: 명세를 모르는 사용자는 "먼저 3승"을 알 수 없음). 화면 문구도 테스트 대상이 되도록 명세에 U-01과 Q-7을 추가.

- 주사위 점을 빨간색으로, 던지기에 **1.2초 굴림 애니메이션** 추가 (작성자 요청: 긴장감). 자동화 영향을 줄이기 위해:
  - 굴리는 동안 `match-section`의 `data-rolling="true"`, 주사위 `data-value`는 빈 값 → 자동화는 `data-rolling="false"`가 될 때까지 기다린 뒤 값을 읽는다
  - 주소에 `?noanim`을 붙이면 애니메이션 0초 (자동화 실행 시간 단축용). 결과 화면 GIF는 애니메이션을 켠 채로 찍는다

- TC 초안 43건 작성(`docs/02-test-cases.md`), 기능별 대표 TC 6건 선정. TC를 쓰며 찾은 통계 검토 포인트 처리:
  - ① 테스트 API로 지정한 눈이 합계 분포에 섞임 → S-02에 "지정 라운드 제외" 명시(Q-8), API 수정. 확인: 2개 분포 표본 984 → 980 (DB의 지정 안 한 라운드 × 2와 일치)
  - ② Grid 정렬 상태가 화면에 안 보임 → 헤더에 ▲▼ 표시, `aria-sort` 속성 추가 (자동화가 정렬 상태를 읽을 수 있게)
  - ③ 기간 역전(시작일 > 종료일) 처리 규칙이 명세에 없음 → TC-F04를 Blocked로 두고 화요일에 SPEC 이슈로 리포트
  - ④ 사람·봇 매치 구분 표시 → 생략

- 통계 Grid 개선 (작성자 요청): 첫 열 "ID" → "매치", 값 `#212` 형식으로 게임 화면과 통일. 최근 20건만 보여주고 "더보기"로 20건씩 추가 (U-02 신설, TC-F14 추가). API에 `offset`과 전체 건수 헤더 `X-Total-Count` 추가. 확인: 212건을 더보기 10회로 모두 불러옴, 중복 0건.

- 초기 데이터 수정 (작성자 관찰: 매치 번호는 작은데 시작 시각이 더 늦은 행이 있음, 예: #59 00:44 vs #176 00:17). 원인은 Generator가 시작 시각을 7일 안에서 무작위로 뽑아서. 기능 결함은 아니지만 **현실에서 생기지 않는 데이터**라 보는 사람이 버그로 오해할 수 있음 → 7일을 매치 수만큼 칸으로 나눠 순서대로 배정하도록 수정. DB를 새로 만들어 재생성: 198건, 10/19~10/26, 번호·시각 순서 어긋남 0건. 같은 seed라 요청 결과(200: 1,065 / 400: 2 / 409: 7)는 이전과 동일.
  - 교훈: 테스트 데이터도 현실적이어야 한다. 비현실적인 데이터는 거짓 결함 보고를 만든다.

- 합계 분포 표 (작성자 요청): 컬럼을 "주사위 합계 · 나온 횟수 · 이론 비율 · 실제 비율" 순서로 바꾸고, 표 위에 이론·실제 비율의 뜻과 세는 방법을 쉬운 말로 설명. "표본 N개" → "지금까지 던진 횟수 N번". 실제와 이론이 조금 다른 것은 표본이 적어서 생기는 정상 현상 (판정은 S-03 조건인 5,000번 이상에서만).

- 통계 표 디자인 (작성자 요청): 진한 헤더, 줄무늬, 행 강조, 정렬 가능한 열은 노란 글씨. 결과(플레이어 승리 초록 / 컴퓨터 승리 빨강 / 무승부 회색), 상태(종료 회색 / 진행 중 주황), 주사위 개수(2개 파랑 / 3개 보라)를 배지 색으로 구분. 칸의 글자는 그대로 두고 색만 입혀 자동화가 읽는 텍스트는 바뀌지 않음.

- 합계 분포 대비 표시 (작성자 요청): 표에 **차이**(실제 − 이론, %p. 파랑 +, 빨강 −)와 **비교** 막대(파란 막대 = 실제, 빨간 선 = 이론, Chart와 같은 색) 열 추가. 열이 좁아 헤더가 줄바꿈되어 Chart를 위, 표를 아래로 배치 변경.

- 플레이어별 승률 정리 (작성자 질문: "이 표가 왜 필요한가?"). 통계 대표 TC(TC-F13)와 BUG-003의 무대라서 유지하되 목적을 드러냄:
  - 제목 "닉네임별 전적 (승률 순위)", 순위 열(1~3위 메달 색), 승률 정의와 정렬 기준 설명. 명세 S-04에 순위 규칙 추가, TC-F15 추가 (총 45건)
  - 봇 20명(bot01~20) → **로마 신화의 신 10명**(유피테르, 유노, 미네르바, 아폴로, 디아나, 메르쿠리우스, 넵투누스, 플루토, 베누스, 바쿠스). 더미처럼 보이지 않게, 표에 스크롤이 생기지 않게. 유노(2자)는 R-06 최소 길이와 같음
  - TC-F01 필터 값 `bot1` → `누스` (넵투누스·베누스), TC-A06·A07 예시도 교체. DB 재생성
  - BUG-003 영향이 순위로 보임: 유노 화면 52.63%(10/19, 6위) vs 올바른 값 58.82%(10/17) → 원래 5위. 결함 리포트에 "순위가 뒤바뀜"으로 영향 기술 예정

### 발견한 결함
- (정식 테스트 전, 고치지 않고 화요일에 리포트) 게임 화면에서 **매치 중에도 주사위 개수 라디오 버튼을 바꿀 수 있음**. 실제 매치에는 영향이 없지만 화면은 바뀐 것처럼 보임 (R-05, TC-A10). 심은 버그가 아니라 TC 작성 중 실제로 발견.
- (관찰, 판단 보류) 닉네임 정렬에서 한글이 영문보다 앞에 옴 (DB 정렬 규칙). 명세에 정렬 기준이 없어 결함은 아님.
- (정식 테스트 전) 개발 중 고친 것 1건: 통계 Grid가 최대 100건만 불러와 "100건"으로 표시됨 → 1,000건까지 불러오도록 수정. 심은 버그가 아니라 실제 실수였음.
