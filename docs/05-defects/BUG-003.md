# BUG-003 승률 계산에 진행 중 매치가 포함되어 승률이 낮게 나오고 순위가 뒤바뀜

| 항목 | 내용 |
|---|---|
| 유형 / 심각도 / 우선순위 | Bug / **Major** / P2 |
| 상태 | Open |
| 관련 규칙 | [S-04](../01-requirements.md) 승률 = 승리 매치 ÷ **끝난** 매치. 진행 중 매치는 제외. 승률 높은 순으로 순위 |
| 관련 TC | ★ [TC-F13](../02-test-cases.md), TC-F15 · 유저 시나리오 [US-03](../02-user-scenarios.md), [US-04](../02-user-scenarios.md) |
| 발견 | 2026-10-27, 김성환, 화면 값과 DB 직접 조회 값 비교 |
| 환경 | Dice Duel v1.0 (`main`), Docker Compose, PostgreSQL 16 |
| 발생 빈도 | 진행 중 매치가 1건이라도 있는 닉네임이면 **항상** |

## 재현 절차
1. 클린 설치 직후 통계 화면을 연다 (http://localhost:8080/stats) → "닉네임별 전적 (승률 순위)"
2. `유노` 행의 값을 확인한다: 전체 매치 19, 끝난 매치 17, 승리 10, 승률 **52.63%**
3. DB에서 S-04 기준 승률을 계산한다
   ```sql
   SELECT nickname,
          count(*) FILTER (WHERE result = 'PLAYER') AS wins,
          count(*) FILTER (WHERE status = 'FINISHED') AS finished,
          round(100.0 * count(*) FILTER (WHERE result = 'PLAYER')
                / count(*) FILTER (WHERE status = 'FINISHED'), 2) AS correct_rate
   FROM matches WHERE nickname IN ('유노', '메르쿠리우스') GROUP BY nickname;
   ```

## 기대 결과
- 유노 승률 = 10 ÷ **17**(끝난 매치) = **58.82%**

## 실제 결과
- 유노 승률 = 10 ÷ **19**(전체 매치) = **52.63%** → 분모에 진행 중 매치 2건이 들어감

| 닉네임 | 승리 | 끝난 매치 | 전체 매치 | 화면 승률 | 올바른 승률 | 차이 |
|---|---|---|---|---|---|---|
| 유노 | 10 | 17 | 19 | 52.63% | **58.82%** | −6.19%p |
| 메르쿠리우스 | 8 | 27 | 28 | 28.57% | **29.63%** | −1.06%p |
| (끝난 매치만 있는 8명) | | | | 같음 | 같음 | 0 |

## 영향: 순위가 뒤바뀐다
초기 데이터 기준(클린 설치 직후):

| 화면 순위 | 닉네임 | 화면 승률 | 올바른 승률 | 올바른 순위 |
|---|---|---|---|---|
| 4 | 바쿠스 | 58.82% | 58.82% | 4 |
| 5 | 플루토 | 54.55% | 54.55% | **6** |
| 6 | **유노** | 52.63% | **58.82%** | **5** |

- 승률이 실제보다 낮게 보이고, **순위가 뒤바뀐다.** 순위표는 사용자가 가장 먼저 보는 화면이라 신뢰도에 직접 영향을 준다.
- 진행 중 매치가 많을수록 더 크게 틀린다. 테스트로 매치를 여러 개 열어 둔 `TCcheck`는 올바른 승률 83.33%(1위)가 화면에서 7.75%(최하위)로 나왔다.
- **[SPEC-001](SPEC-001.md)과 겹친다**: 도중에 떠난 매치가 영원히 "진행 중"으로 남으므로, 이 결함의 영향은 시간이 갈수록 커진다.

## 회귀
- 수정 후 TC-F12·F13·F15를 다시 수행한다. 진행 중 매치가 있는 닉네임과 없는 닉네임을 함께 비교해야 한다.
